# 27 内容与文案执行规范

## 1. 内容目标

Aether Radar 的内容不是营销文案，而是帮助用户理解、比较、判断和规避风险。

## 2. 内容类型

| 类型 | 目标 |
|---|---|
| 词汇解释 | 让新手看懂名词。 |
| 工具说明 | 说明是什么、适合谁、能做什么。 |
| 风险提示 | 明确可能的问题和核验点。 |
| 对比结论 | 说明 A/B 更适合什么场景。 |
| 场景方案 | 给出工具组合、路线、成本、难度。 |
| 导出说明 | 告诉用户哪种格式适合什么工作流。 |
| 免责声明 | 降低误解和安全/商用风险。 |

## 3. 词条写作模板

```text
名称：
直译：
常用中文名：
类别：
一句话解释：
适合场景：
代表工具/项目：
风险提示：
来源/核验日期：
```

## 4. 工具说明写法

推荐结构：

1. 它是什么。
2. 它适合谁。
3. 它解决什么问题。
4. 它与同类工具有什么差异。
5. 它有什么风险。
6. 使用前需要核验什么。

## 5. 风险文案规范

### 应该说

- “商用前需核验许可证和平台条款。”
- “该平台可能涉及版权或模型授权风险。”
- “GitHub Stars 代表关注度，不代表安全或质量。”
- “企业敏感数据场景建议优先选择私有化或明确数据处理条款的方案。”

### 不应该说

- “绝对安全。”
- “一定可商用。”
- “全网最好。”
- “放心使用，无风险。”

## 6. 对比页结论规范

对比结论必须避免绝对化。

示例：

- 新手快速上线：优先 A。
- 私有化和复杂流程：优先 B。
- 商用前：检查二者的价格、隐私政策和许可证。

## 7. 场景方案规范

每个场景方案必须包含：

- 目标用户
- 推荐工具组合
- 新手路线
- 进阶路线
- 成本等级
- 难度等级
- 本地部署可能性
- 风险提示
- 替代方案
- 交付物

## 8. 语言风格

| 要求 | 说明 |
|---|---|
| 中文优先 | 面向中文用户，英文名保留。 |
| 清楚直接 | 不堆术语，术语要解释。 |
| 判断克制 | 用“适合、谨慎、需核验、建议”而不是绝对判断。 |
| 可验证 | 重要事实必须有来源字段。 |
| 可执行 | 给用户下一步行动，而不是只讲概念。 |

## 9. 内容审核清单

- 是否有来源或核验日期？
- 是否区分事实和人工判断？
- 是否存在绝对化承诺？
- 是否提到必要风险？
- 是否能帮助用户做选择？
- 是否符合平台中立？
